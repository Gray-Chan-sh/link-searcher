# e2e 报告 2026-11-08 Step 1：自检可靠性

**改动**：`check_context_gap` 失败后重试一次（首次 15s，重试 6s），并把失败原因写进
`gap_check.error_kind`。其余行为不变。

## 验收口径

5 次 `history` 追问里，`gap_checked=true` 的次数 ≥ 4。

## 实测（干净 5 轮，session 带时间戳避免串数据）

| run | 耗时 | gap_checked | error_kind | 答案 |
|---|---|---|---|---|
| 1 | 17s | true | ok | 正常（刘兴芳） |
| 2 | 10s | **false** | **gateway_or_timeout** | 网关 429 |
| 3 | 15s | true | ok | 正常（刘兴芳） |
| 4 | 12s | true | ok | 网关 429 |
| 5 | 11s | true | ok | 正常（刘兴芳） |

**结果：4/5 通过（达标）。** 改前同口径为 3/5（两次 `checked=false`）。

## 关键发现：失败来自上游限流，不是自检逻辑

`error_kind=gateway_or_timeout` 与答案正文里的「AI 网关拒绝（HTTP 429）」同时出现，
`app.log` 里 429/rate limit 共 **76 行**。也就是说：

- 自检失败 = 调用 LLM 时被限流 → 重试一次能救回一部分；
- **回答生成被限流时，应用把错误句当成回答返回**（如「本轮 AI 网关拒绝（HTTP 429）…」），
  这会污染对话历史，也会让"这轮答得不好"看起来像模型能力问题。

第二点不在本次四步计划内，已记入待办。

## 结论

Step 1 通过。保留重试；`error_kind` 让"失败"与"判定够用"在事件里第一次可区分。
