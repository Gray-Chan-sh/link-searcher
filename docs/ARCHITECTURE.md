## 一、总体设计思想

### 这个程序是什么

Link-Searcher 是一个**本地全文搜索 + AI 文档问答**的桌面应用。它的核心使命是一句话：

> **把你硬盘里的所有文档，变成一个"能全文检索、能直接提问"的私有知识库。**

### 三个核心问题

任何"本地文档智能搜索"程序都要回答三个问题：

| 问题 | Link-Searcher 的回答 |
|------|----------------------|
| 文件内容从哪来？ | 一个统一的**文本提取管线**，把 PDF/Word/图片/音频等 20+ 格式统一转成纯文本 |
| 怎么搜索？ | 全文搜索引擎（关键词）+ 语义向量引擎（意思）**双路融合** |
| 怎么回答？ | RAG 管线：检索相关文档 → 组装上下文 → 交给 LLM 回答 |

### 设计的两条主线

1. **性能优先**：索引和搜索要快（毫秒级），因此全文搜索用原生高性能引擎，文本提取用多线程并行。
2. **隐私可选**：核心搜索完全本地，AI 是可选项。用本地模型做语义搜索不出机器；用远程大模型才把内容发出去（用户知情）。

### 为什么用 Rust + Tauri + SQLite 这套组合

| 选择 | 设计理由 |
|------|---------|
| Rust | 性能、内存安全、无垃圾回收，适合大量文本处理与并发 |
| Tauri | 用 Web 技术（React）写界面，但底层是原生性能，比 Electron 轻量 |
| SQLite | 零配置、单文件、稳定可靠，够用且不过度设计 |

### 复现路线图（七个里程碑）

```
第 1 步：打通文本提取（任意文件 → 纯文本）
第 2 步：接入全文搜索索引（关键词检索）
第 3 步：目录扫描 + 文件监控（增量更新）
第 4 步：接入 AI 对话能力（流式生成）
第 5 步：语义向量检索（按"意思"检索）
第 6 步：组装 AI 聊天（检索 + 材料 + 回答）
第 7 步：加 Web 访问 + 共享前端
```

## 二、模块一：全文搜索引擎

### 解决什么问题

用户输入关键词，要在**几毫秒内**从几十万个文件中找出相关文件。这是整个软件的地基，没有它后面都谈不成。

### 核心思想

**索引先行**：文件内容在导入时就被"切碎、分析、建索引"，搜索时不再去翻原始文件，而是查这个已经排好序的索引结构，所以极快。

**倒排索引**：核心数据结构是"词 → 文件列表"。要搜"判决"，直接查表得到所有含"判决"的文件，而不是逐个文件找。

**中文要分词**：英文按空格切词，中文必须靠分词器。例如"判决结果是什么"需要被切成 `判决 / 结果 / 什么`，否则整句当作一个词搜不到。

### 核心架构

```
┌─────────────────────────────────────────────┐
│  索引管理器（IndexManager）                    │
│  持有读端（Reader）+ 写端（Writer）            │
│  启动时打开或创建索引                          │
└────────────────────┬────────────────────────┘
                     │
        ┌────────────┴────────────┐
        │                         │
┌───────▼────────┐       ┌────────▼───────┐
│  字段定义 Schema │       │  查询引擎 Searcher│
│  正文 content    │       │  相关性 BM25 排序│
│  文件名 path     │       │  模糊容错 1 字   │
│  时间 mtime      │       │  搜索建议       │
└───────┬────────┘       └────────┬───────┘
        │                         │
        └────────────┬────────────┘
                     ▼
            中文分词器（jieba）
            （写入和查询共用同一套分词）
```

### 关键设计决策

1. **字段最小化**：只索引"正文 + 文件名 + 时间"。够用，不多加字段，索引更小更快。
2. **同一套分词**：写入和查询共用同一分词器，保证"怎么写就能怎么搜到"。
3. **容错一个字符**：用户打错一个字也能匹配，提升体验。
4. **读端缓存**：搜索频繁，复用同一个读端避免反复打开磁盘。

### 边界与取舍

- 只索引文本，二进制（视频等）靠提取管线先转文本。
- 排序默认按相关性（BM25），可选按时间/大小。
- 不做复杂布尔语法以外的花哨功能，保持简单。

## 三、模块二：文本提取管线

### 解决什么问题

搜索引擎只认文本。但硬盘里有 PDF、Word、Excel、PPT、图片、音频、压缩包……需要统一的"任意文件 → 纯文本"转换器。

### 核心思想：格式路由

不针对每种格式写死一套代码，而是做一个**总路由**，根据文件扩展名把任务分发给对应的提取器。这样新增一种格式，只需加一个提取器，主流程不用改。

```
                   总路由（按扩展名分发）
                         │
    ┌────────┬────────┬──┴───────┬────────┬────────┐
    ▼        ▼        ▼          ▼        ▼        ▼
  PDF提取  Office  图片OCR     音频转写  纯文本   压缩包
  (扫描件  (Word/  (光学识别   (语音转写＋ (直接读)  (解包后
  才 OCR)  Excel/  文字)        说话人)            逐个走管线)
          PPT)
```

### 各提取器的设计要点

| 提取器 | 处理什么 | 设计要点 |
|--------|---------|---------|
| PDF | PDF 文档 | 能抽文本就抽；扫描件（纯图片的 PDF）才交给 OCR |
| Office | Word/Excel/PPT | **纯本地解析，不给用户装 Office 的负担** |
| 图片 | 图片文件 | 不做别的，就是 OCR 识别文字 |
| 音频 | mp3/wav 等 | 语音转文字 + 说话人分离（法庭录音等场景） |
| 纯文本 | 文本/代码 | 最直接，是兜底 |
| 压缩包 | zip/tar 等 | 解包后逐个条目走对应提取器 |

### 关键设计决策

1. **一个文件、一套结果**：提取出文本的同时，记录内容哈希、字符数、是否用过 OCR，供后续去重和统计。
2. **OCR 多引擎降级**：内置 OCR → 系统自带 → 备选引擎，按可用性自动降级，保证尽量识别出文字。
3. **内容去重**：相同内容哈希的文件只提取一次，后续直接复用，省时省资源。
4. **只存文本不存源文件**：数据库只存提取出的文本，不复制原文件，节省空间。

### 边界与取舍

- 未知格式也尝试纯文本兜底，尽量不丢文件。
- 支持格式是"白名单优先 + 黑名单排除"（临时文件、隐藏文件、缓存目录等天然排除）。

## 四、模块三：目录扫描与文件监控

### 解决什么问题

文件是**活的**——会被新增、修改、删除。索引必须跟着变，否则搜到的是过期数据。

### 核心思想：增量更新

全量扫描很慢，但大多数时候文件没变。所以设计成**只处理"变了"的文件**，没变的直接跳过。这样日常维护近乎零成本。

```
                    ┌─────────────────────────────────────┐
                    │  扫描器（Scanner）                     │
                    │  全量扫描 / 增量扫描 / 启动扫描        │
                    │  每个文件：                           │
                    │    ① 排除规则过滤                     │
                    │    ② 查台账：时间变过吗？索引过吗？     │
                    │    ③ 需要才交给索引器                 │
                    └──────────────┬──────────────────────┘
                                   │
                  ┌────────────────┴────────────────┐
                  ▼                                 ▼
        ┌──────────────────┐              ┌──────────────────┐
        │ 实时监控（Watcher）  │              │  索引器（Indexer）  │
        │ 监听文件系统事件    │              │  多线程并行提取文本  │
        │ 300ms 防抖批量处理  │              │  定期提交防丢进度    │
        └──────────────────┘              └──────────────────┘
```

### 关键设计决策

1. **相对路径存储**：数据库存"相对路径"（相对监控根），机器/系统变了路径不变，可跨平台共享索引。
2. **内容哈希辨识移位**：文件内容没变但路径变了，靠哈希识别是"搬家"而非"删除+新建"，保留原索引。
3. **定期自动提交**：每处理一批就提交一次，防止崩溃丢全部进度。
4. **实时监控防抖**：文件变化事件密集，用 300ms 防抖合并处理。

### 边界与取舍

- 超大目录扫描有超时保护，避免卡死。
- 排除规则含默认（隐藏/临时/缓存）+ 用户自定义 glob。

## 五、模块四：AI 出口（LLM 网关）

### 解决什么问题

程序如何与外部大语言模型（LLM）对话。这是所有 AI 功能的共同底座。

### 核心思想：一套协议通吃

绝大多数 LLM 服务（Ollama、OneAPI、vLLM、各类中转）都实现了 OpenAI 兼容的对话接口。**只对接一种协议，就能用上所有模型**，不必为每家厂商写适配器。

```
┌──────────────────────────────────────────┐
│            AI 出口（LLM 网关）              │
│                                           │
│  非流式对话：问一句 → 等完整答案 → 返回       │
│  流式对话：问一句 → 逐字回调 → 打字机效果    │
│  向量编码：文本一句话 → 转成数字向量          │
│  提供商解析：选当前启用的那个提供商            │
└──────────────────────────────────────────┘
```

### 关键设计决策

1. **提供商抽象**：一个"提供商" = 网关地址 + 密钥 + 模型列表。用户可以配多个，分别选一个做语义、一个做对话。
2. **优雅降级**：没配置时，AI 出口直接返回"不可用"，前端隐藏 AI 功能，普通搜索不受影响。
3. **流式优先**：对话默认流式，逐字推给前端，体验像打字机；网关不流式时就自动回退。
4. **可取消**：一个全局"取消标记"，流式读取时随时检查，用户点取消能立即终止。
5. **失败不崩溃**：网关挂了或配置错了，返回空结果而不是让程序崩溃。

### 边界与取舍

- 有的模型把回答放在"推理"字段而非"正文"，需要做字段回退。
- 连接要设超时，避免卡死；但流式读取缺少全局超时（已知取舍）。

## 六、模块五：语义向量检索

### 解决什么问题

关键词搜索查"字面"，但用户往往想查"意思"。搜"欠费催缴"，语义上也应命中"逾期未缴纳物业管理费"。这就是语义搜索。

### 核心思想：把文本变成数字

一段文本 → 一串数字（如 1024 维向量）。**语义相近的文本，向量距离近**。判断两个文本是否相关，就看它们向量的夹角（余弦相似度）。

```
    "猫是一种宠物"  →  [0.2, 0.8, ...]   ┐
    "The cat is a pet" → [0.22, 0.79, ...] │ ← 角度小，语义相近
    "今天天气很好"  →  [0.9, -0.3, ...]  ┘    ← 角度大，语义无关
```

### 为什么用本地模型

- **隐私**：默认的语义模型在本地用 CPU 推理，文档内容不出机器。
- **中文优化**：用的中文语义模型，效果优于通用英文模型。

### 语义检索怎么用

```
用户搜索 → 把查询也转成向量 → 和库里的每个文件向量算相似度
        → 过滤掉低于阈值的 → 按相似度排序 → 得到候选文件
```

### 关键词 + 语义融合

两种检索各有优劣：
- **BM25（关键词）**：精确、可靠，但搜不到"意思一样、字不一样"的文件。
- **语义**：能找"意思"，但可能不够精确、有噪声。

所以做个**加权融合**：

```
最终分 = 30% × 语义分 + 70% × 关键词分
（比例用户可调）
```

关键词仍占主导（可靠），语义提供"寻意外"的补充。语义只是锦上添花，不喧宾夺主。

### 边界与取舍

- 语义是"全表扫描"（把每个向量都比一遍），量大时慢——这是为简单牺牲速度的取舍。
- 只在配置了模型且开关打开时才启用，否则纯关键词搜索。

## 七、模块六：AI 聊天与 RAG 管线

### 解决什么问题

`会话式文档问答`：用户既能直接问"判决结果是什么？"，也能限定范围（指定某文件、某类型、某目录），程序检索相关文档后让 LLM 基于材料回答，还能多轮追问。

### 核心思想：RAG（检索增强生成）

> **不要问 LLM"它记住的问题"，而是先把相关文档找出来塞给它，再让它基于这些材料回答。**

好处：
- 回答有据可依，不凭空捏造
- 可以标注来源（"这个结论出自哪份文件"）
- 模型不需要"预装"你的私有知识

### RAG 管线五步

```
┌────────────┐  ┌────────────┐  ┌────────────┐
│ 查询改写     │→│ 范围解析     │→│ 三路检索     │
│ 补全省略句  │  │ 理解限定条件 │  │ 找候选文件   │
└────────────┘  └────────────┘  └─────┬──────┘
                                      ▼
┌────────────┐  ┌────────────┐  ┌────────────┐
│ LLM 回答    │←│ 组装上下文   │←│ 三层注入     │
│ 流式生成    │  │ 拼成提示词  │  │ 精挑内容    │
└────────────┘  └────────────┘  └────────────┘
```

#### 第 1 步：查询改写
多轮对话里用户会说"它的风险呢？"这种省略句，必须补全成可检索的完整句。先尽量用规则补全，可选再让 LLM 润色；规则保底，LLM 失败也不影响。

#### 第 2 步：范围解析
理解用户注入的限定：`@某文件`、`@目录`、`某类型`、`日期范围`、`全库`。输出一组过滤条件，决定"在哪些文件里找"。

#### 第 3 步：三路检索
- ① 关键词命中（BM25）
- ② 语义命中（向量）
- ③ 文件名匹配（SQL 模糊）

三路合并去重，得到候选文件集合。

#### 第 4 步：组装上下文
把候选文件的内容整理好，拼成给 LLM 的提示词。这是 RAG 最关键的部分——**决定 LLM 能看到什么**，见下节"三层注入"。

#### 第 5 步：LLM 回答
流式生成，逐字推给前端，完成后结束本轮。

### 核心：上下文三层注入

LLM 的上下文窗口有限，不能把几万条命中全塞进去。所以设计成三层，越重要越优先：

```
Layer 0：引用文档（用户 @ 指定的文件）
  → 用户明确要求看的，全部注入，最可靠
  → 内容太长时按与查询相关的分块截断

Layer 1：关键词命中补全
  → 自动检索到、未被引用的文件
  → 默认最多 30 份全文，"全量召回"开启则全部
  → 每份按"总预算 ÷ 份数"分配篇幅

Layer 2：剩余命中摘要
  → 超出 Layer 1 的命中，批量生成简述摘要兜底
  → 最多 60 份，并行生成
```

**设计动机**：
- 用户**明确要求看**的（Layer 0）最可靠，全进。
- 自动检索的（Layer 1）按预算精选，不浪费上下文。
- 其余的（Layer 2）用摘要兜底，不遗漏大方向。

### "仅依据文档"严格模式

一个开关。开启后：
- 用户引用的文件必须在检索结果里（找不到/有空内容就报错）。
- 范围内没检索到任何材料时，**拒绝回答**而不是让模型瞎编。
- 旧对话里的来源文件不混入本轮。

**设计动机**：用户引用了文件，说明答案必须基于它；要么有依据地答，要么老实承认"没找到"，这比编造强。

### "全量召回"开关

控制 Layer 1 是注入 30 份还是全部命中。**只影响非引用文档的自动注入量**，不影响用户 @ 的文件。

### 内容为什么可能遗漏（6 个截断点）

| # | 截断发生在哪 | 会丢什么 | 什么条件下 |
|---|-------------|---------|-----------|
| 1 | 引用文档 | 超 50k 字符的部分 | 引用文档很大 |
| 2 | 关键词命中 | 30 份之后的 | 全量召回关闭 |
| 3 | 每份命中 | 超配额的部分 | 命中很多，每份配额少 |
| 4 | 剩余摘要 | 60 份之后的 | 总命中很多 |
| 5 | 总长度 | 拼起来超 50k/140k | 始终存在 |
| 6 | 语义命中 | 500 条之后的 | 全量召回关闭 |

**结论**：最容易遗漏的是"引用了超长文档"的场景；"全量召回"能缓解 2 和 6，但 1/3/4/5 始终存在。

### 边界与取舍

- 内容截断从开头截，可能丢文档末尾的结论（无位置感知）。
- 上下文窗口大小是硬编码的，不随模型调整。
- "全量召回"塞更多会挤占每文件的篇幅，要权衡。

## 八、模块七：会话与事件系统

### 解决什么问题

1. AI 聊天是多轮的，需要把会话（历史、检索范围、每轮证据）持久化。
2. 流式生成要实时推给前端，需要事件通知机制。
3. 桌面（原生）和浏览器（Web）两种使用场景要共享同一套前端。

### 会话存储

- 会话存成一个 JSON 文件，每个人含：标题、消息列表、来源文件、检索范围、每轮的证据。
- 前端的"思考中"状态由一个"发送时间戳"驱动：发送时记下时间，收到完成事件清除。

### 事件系统：桌面自带的，网页靠桥

桌面端用框架自带的事件总线（发事件 → 监听到）。浏览器没有这套，所以做一个**事件桥**：

```
 桌面/后端 发出 ai-chunk（流式片段）
      │   事件桥捕获
      ▼
 事件通道（广播）
      │
      ▼
 网页 /api/events（消息流）→ 浏览器实时收到
```

```ascii
┌──────────────────────────────────────────────┐
│                事件总线                        │
│  发送 ai-chunk（流式片段）                     │
│       ├─→ 桌面前端实时收到 → 打字机效果        │
│       └─→ 事件桥 → 网页前端实时收到           │
│  发送 ai-done（回答完成）                     │
│       ├─→ 桌面前端 → 结束"思考中"             │
│       └─→ 事件桥 → 网页前端 → 结束"思考中"    │
└──────────────────────────────────────────────┘
```

要桥接的事件在"白名单"里列出来。`ai-progress`（进度条）不在白名单，所以网页模式看不到阶段进度条——这是一个已知取舍。

### 前端"思考中"状态机

```
发送      → 记时间戳 → 显示"思考中" + 取消按钮
流式片段  → 逐字追加显示
回答完成  → 清除"思考中" → 显示完整回答 → 保存会话
取消      → 终止生成 → 保留已输出的 + "已取消"
```

### 边界与取舍

- 会话文件没有版本迁移机制，靠字段默认值兜底。
- "完成"回调会检查"是否还在思考中"，若时序出错可能丢掉回复（已知取舍）。

## 九、模块八：Web API 服务器

### 解决什么问题

桌面应用只能在本地用。加一层 Web API 后，**同一套前端代码也能在浏览器里跑**（远程访问、移动设备、演示尝鲜）。

### 核心思想：复用一切

- 后端命令逻辑完全复用，只是外面包一层 HTTP 路由 + 鉴权。
- 前端检测运行环境：桌面走原生通道，浏览器走 HTTP，**界面代码一行不用改**。
- 事件靠上一节的事件桥把流式结果推给浏览器。

### 安全设计

- **HTTPS 加密**：用自签名证书，防明文传输。
- **令牌鉴权**：所有接口都要带"令牌"（token），不能随便访问。
- 可配置端口和绑定地址。

```
   浏览器（React 前端）
        │  发送 HTTP 请求 + 令牌
        ▼
  ┌────────────────────────────┐
  │  Web API 服务器             │
  │  鉴权 → 路由分发 → 后端命令   │
  │  事件桥 → 把流式结果推回浏览器 │
  └────────────────────────────┘
        │
        ▼
  复用 Tauri 后端全部逻辑
```

### 边界与取舍

- 自签名证书会被浏览器提示"不安全"，需手动放行。
- 服务跑在应用主进程内，若大模型处理卡顿可能影响界面响应（已知取舍）。

## 十、模块九：数据存储

### 设计哲学

一个数据库文件存所有关系型数据，几张表各司其职：

| 表 | 存什么 | 为什么这样设计 |
|----|--------|--------------|
| 文件台账 | 每个文件：路径/时间/大小/内容哈希/状态/索引标记 | 文件情况的"登记簿" |
| 内容索引 | 每个文件的提取文本（按内容哈希关联） | 内容缓存，去重 |
| 分块表 | 大文件切成小块 | 支持按块检索大文件 |
| 向量表 | 每文件的语义向量 | 语义检索 |
| 摘要表 | 每文件的 AI 摘要 | 摘要缓存，避免重复生成 |
| 目录配置 | 监控目录 | 目录管理 |
| 搜索历史 | 历史搜索 | 历史记录 |
| 错误表 | 索引失败记录 | 可诊断 |
| 设置表 | 键值设置 | 通用设置 |
| 事件表 | AI 推理事件链 | 追溯"这次回答为什么用了这些文档" |

### 关键设计决策

1. **索引状态用枚举**：未索引 / 已索引 / 提取中 / 已提取，配合部分索引快速找"待处理"文件。
2. **内容哈希当钥匙**：去重的核心——相同内容只存一份全文，多个文件复用。
3. **软删除**：文件删除标记一下而非物理删行，便于追溯与恢复。
4. **连接池**：多线程访问数据库需要池，避免并发阻塞。

### 边界与取舍

- 单文件数据库简单够用，但并发写能力有限。
- 不引入重型数据库（Postgres/Mongo），避免过度设计。

## 十一、模块十：前端架构

### 设计思想

一套 React 前端，两种运行环境（桌面 / 浏览器），通过环境检测自动切换数据层。界面代码与数据层解耦，所以两处都跑同一套 UI。

### 页面地图

| 页面 | 职责 |
|------|------|
| 搜索页 | 关键词/筛选/预览 |
| AI 聊天页 | 会话 + 对话 |
| 浏览页 | 表格浏览所有文件 |
| 资料库 | 目录管理 |
| 索引状态 | 进度与统计 |
| 设置 | 配置 |
| 日志 | 查看日志 |

### AI 聊天面板（前端最复杂的组件）

```
AI 聊天面板
├── 消息列表（用户/助手 + 富文本渲染）
├── 检索依据面板（每份来源：评分 + 路径 + 片段）
├── 推理时间线（这次回答经历了哪些步骤）
├──"思考中"指示器 + 取消按钮
├── 范围条（已加入的文件/目录 chips）
├── 开关（仅依据文档 / 全量召回）
└── 输入框 + 发送按钮
```

### 会话状态管理

- 父组件持有"当前会话"状态，传给聊天面板。
- 面板通过回调 + 局部更新来改会话。
- 每次变更自动保存，切走再切回能恢复。

### 边界与取舍

- 浏览器模式首次加载有令牌竞态的可能（已知取舍）。
- 前端组件较大（聊天面板数百行），但逻辑集中在单文件方便维护。

## 十二、模块间数据流总览

```
                 ┌───────────────────────────┐
                 │       前端（React）          │
                 │  搜索页 / 聊天面板 / ...    │
                 └────────────┬──────────────┘
                              │ 自动切换通道
                 ┌────────────┴─────────────┐
                 ▼                          ▼
        ┌───────────────┐          ┌────────────────┐
        │ 桌面原生通道   │          │ Web 访问（HTTP） │
        └───────┬───────┘          └────────┬───────┘
                │                           │ 事件桥
                ▼                           ▼
        ┌────────────────────────────────────────────┐
        │                Rust 后端                    │
        │   对话命令 / 搜索命令 / 索引命令 / 会话命令     │
        └────────┬─────────────┬──────────────────────┘
                 │             │
        ┌────────▼─────┐  ┌───▼──────────────────┐
        │  AI/RAG 管线  │  │  搜索引擎＋语义检索      │
        │  改写→范围→    │  │  （关键词＋向量）        │
        │  检索→注入→LLM │  └──────────┬───────────┘
        └────────┬─────┘             │
                 │                   │
        ┌────────▼─────────┐  ┌─────▼────────┐
        │  大模型网关（外部） │  │  数据库（SQLite）│
        │  对话 + 向量编码    │  │  台账/内容/向量 │
        └──────────────────┘  └──────────────┘

  —— 另有：文件系统（原文）↔ 扫描器 ↔ 提取管线 ↔ 索引器
```

### 一条完整请求的旅程

以"问：判决结果是什么？"为例：

```
1. 用户输入 → 前端聊天面板
2. 前端发送 → 后端对话命令（桌面走原生 / 网页走 HTTP）
3. 查询改写 → 补全成可检索的完整句
4. 范围解析 → 决定在哪找
5. 三路检索 → 从索引+向量+数据库找候选文件
6. 三层注入 → 把候选文件内容按优先级组装
7. 大模型响应 → 流式逐字返回（走事件桥到前端打字机显示）
8. 完成 → 记录推理事件 + 保存会话
```

## 十三、核心设计原则

1. **性能优先**：全文搜索毫秒级，多线程并行索引，增量更新。
2. **隐私可选**：核心全本地，AI 是可选且用户知情。
3. **优雅降级**：没配大模型 → AI 隐藏；模型挂了 → 返回空而非崩溃；没语义 → 纯关键词。
4. **够用不过度设计**：能用 SQLite 就不上重型数据库，能用标准库就不引框架。
5. **一套代码两处跑**：前端桌面/网页复用，后端命令原生/网络复用。
6. **回答内容诚实**：RAG 必须基于材料，"仅依据文档"宁可拒绝也不编造。

## 十四、已知取舍与未来方向

### 当前取舍（可接受）

| 取舍 | 为简单付出的代价 | 未来改进 |
|------|----------------|---------|
| 语义搜索全表扫 | 量大时慢 | 换高级向量索引 |
| 内容从开头截 | 可能丢末尾结论 | 分块重排，取最相关块 |
| 上下文窗口写死 | 不随模型调整 | 按模型动态调整 |
| 网页模式没进度条 | 看不到阶段 | 补进事件白名单 |
| Web 服务与应用同进程 | 可能互相卡 | 独立进程 |

### 未来方向

- 向量检索换高级索引（替代全表扫描）
- 分块 + 重排（更精准的内容注入）
- 会话版本的迁移机制
- 流式读取超时控制
- 多模型自动路由（改写/检索/回答用不同模型）
