# RAG 评测集 v2 设计（Golden v2）

> 本文只写**方法论与规范**。真实题目、支撑文件与逐字引文属于客户语料，
> 存放于数据目录的 `eval-golden/golden.jsonl`，**不入 git**。

---

## 1. 为什么要重写

v1 评测集回答的是**一个**问题：*"含答案的文件有没有被找到"*。它的指标是
`Context Recall@10`（只看 `support_files` 的 basename 有没有出现在注入列表前 10）。

这与实际使用需求不匹配，有三处系统性偏差：

| 偏差 | v1 做法 | 实际需求 |
|---|---|---|
| **粒度** | 文件级 | **段落级**：文件进了，答案那一段有没有真的送进上下文 |
| **题型** | 绝大多数是"取值型"（X 是多少）——系统本就最擅长的场景 | **说理型**（为什么认定 / 依据是什么） |
| **轮次** | 单轮独立问句，无指代 | **多轮追问**（指代、角色切换、范围继承） |

此外 v1 未覆盖两个真实失败模式：

- **来源角色错配**：同一事实常同时存在于裁判文书、当事人文书、自制说明中；
  回答把"当事人主张"当成"法院认定"来引，v1 无法度量。
- **格式/OCR 差异**：对话体笔录无结构化路标；部分扫描件 OCR 输出**字间带空格**，
  使关键词检索失效。

v2 **重写**（替换 v1，不追加）。v1 的 88 题保留为**回归基线**（备份不删），
用于守住既有能力不倒退。

---

## 2. 设计原则

1. **按文书类型铺，不盯单一格式路标**
   格式化裁判文书有"本院认为/综上/判决如下"这类现成路标；但笔录（对话体）、
   表格（xlsx）、扫描件表单、超长法规都没有。题目必须覆盖这些类型。
2. **难点分层**，每类都要有代表题：

   | 难点 | 说明 |
   |---|---|
   | 长文档后部 | 答案位于文档 80%+ 位置，按"从开头截断"的注入策略必然丢失 |
   | 对照组（浅） | 答案在文档开头，用于检测改动是否引入回归 |
   | 对话体无路标 | 答案夹在庭审/质证对话里 |
   | 超长法规 | 十万字级，答案在 60%+ |
   | 表格数值 | xlsx 结构化数据取值 |
   | 字间空格 | OCR 输出每字之间有空格，关键词匹配失效 |
   | 来源角色 | 同事实多角色并存，考验引用是否对齐问题所问 |

3. **判定必须客观可复现**：答案位置用**逐字引文**锚定，不用人工印象。

## 3. 数据模型

```jsonc
{
  "id": "A4",
  "session": "wjy-hz",        // 多轮会话分组；单轮题填自身
  "turn": 0,                   // 会话内轮次（0 起）

  "question": "……为什么认为……不足以证明……？",
  "category": ["reasoning", "long_doc", "role_mismatch"],

  // L1：含答案的文件（basename 在全库唯一）
  "support_files": ["案件/…/一审判决书.pdf"],

  // L2：答案位置。quote 为主锚点，offset 仅作提示
  "answer_spans": [{
    "path": "案件/…/一审判决书.pdf",
    "quote": "该证据仅证明其与案涉房屋所有权人存在利害关系",
    "char_range": [8135, 8197],
    "chunk_index": 6,
    "position_pct": 79
  }],

  // L3：问题所问的角色 + 易混入的异角色文书
  "expected_role": "court_finding",
  "role_distractors": [
    { "path": "案件/…/二审行政上诉状.docx", "role": "party_claim" }
  ],

  // 人工写的答案要点（供回答层判定，避免主观）
  "answer_gist": "法院认为只提交亲属关系证据仅能证明存在利害关系，不足以证明登记确有错误"
}
```

### 3.1 为什么 `quote` 是主锚点

- `char_range` 会随 OCR / 提取实现变化漂移；
- `chunk_index` 会随分块参数（阈值、块长）变化漂移；
- **逐字引文**最稳。定位失败时才退回 offset 并告警。

### 3.2 引文匹配的归一化规则（实测踩坑）

**必须同时做两件事**，否则引文会定位失败：

1. **去空白**：OCR 常在句中插入换行（如 `所有权人\n存在利害关系`）
2. **统一全半角标点**：OCR 常输出半角逗号 `,`，而人工录入习惯用全角 `，`

规范化后比较，命中后再把位置映射回原文偏移，用于计算 `char_range`。

> 若语料存在**字间空格**（每字之间插空格），去空白后即可正常匹配——
> 这类文档的关键词检索会失效，但引文定位仍可用。

## 4. 分类体系

| 类别 | 说明 |
|---|---|
| `reasoning` | 说理/论证型："为什么认定""依据是什么" |
| `long_doc` | 答案位于文档 50% 之后（v2 强制标注 `answer_spans`） |
| `role_mismatch` | 同事实多角色并存，考验引用角色是否对齐 |
| `dialogue` | 对话体（庭审/质证/询问笔录），无结构化路标 |
| `table` | 表格类数值取值 |
| `sparse_ocr` | 字间空格等 OCR 异常格式 |
| `multiturn_pronoun` | 追问含指代（他/它/该） |
| `multiturn_role` | 追问切换所问角色（判决书 → 上诉状） |
| `multiturn_scope` | 追问切换/继承检索范围 |
| `fact` / `semantic` / `twin` / `multi_hop` | 沿用 v1 分类 |

---

## 5. 指标

分两层，避免把**确定性**的检索行为和**非确定性**的模型行为混在一个数字里。

### 5.1 检索/注入层（`--dry-run`，确定性、可作门禁）

| 指标 | 定义 | 抓什么 |
|---|---|---|
| `File Recall@10` | 沿用 v1 | 文件没找到 |
| **`Span Hit`** | `answer_spans` 是否落在**被注入**的字符区间内 | 答案段没进上下文 |
| `Span Rank` | 含答案段的文书在注入列表中的名次 | 排序质量 |
| `Expected-Role Source Injected` | `expected_role` 对应文书是否被注入 | 角色来源缺席 |
| `Scope Leak` | 全库提问时注入的非本案文件数 | 跨案污染 |

### 5.2 回答层（需真实 LLM 调用）

| 指标 | 定义 |
|---|---|
| `Role Match` | 回答中 `[N]` 所指文书的角色 == `expected_role` |
| `Quote Fidelity` | 回答标"原文…"的引文，是否在**被引文档**中逐字存在 |
| `Pronoun Resolved` | 追问指代解析结果 == 人工标注的指代对象 |

> `Quote Fidelity` 的必要性来自实测：回答曾把改写后的句子标为"原文认定"，
> 而该句在任何文档中都不逐字存在。

## 6. 工具改动（P0）

1. **`chat --dry-run --dump-injected`**
   现状只打印 `path=`，看不到注入了哪些文字。改为额外打印每份材料的
   **注入字符区间**，例如：
   ```
   [  4] path=…/一审判决书.pdf injected=4553 spans=[0-1500, 7764-9260, 1300-2797]
   ```
   实现：让内容组装函数除返回文本外，一并返回覆盖的字符区间。

2. **`chat --history <json>`**
   现状 CLI 是单轮。改为可从文件读取 `[{role, content}, …]` 作为对话历史
   （底层 `prepare_conversation_prompt` 已接受 messages 数组，仅需在 CLI 暴露）。

3. **评测脚本**：解析 `answer_spans`（引文归一化定位）、按会话回放多轮、
   输出上述指标。建议拆成两个脚本：检索/注入层（确定性）与回答层（需 LLM）。

---

## 7. 规模与分期

| 期 | 内容 | 验收 |
|---|---|---|
| **P0** | `answer_spans` + `--dump-injected` + `Span Hit` | 长文档后部题的 Span Hit 由 ❌ → ✅ |
| P1 | `expected_role` + `role_distractors` + 角色指标 | 角色来源命中率有数字 |
| P2 | `--history` + 多轮会话 + 指代/范围指标 | 指代解析率有数字 |

题量控制：**总题数不宜大**（回答层指标需真实 LLM 调用）。多轮会话占比应显著
提高，因为它是实际使用的主要形态，且 v1 完全未覆盖。

## 8. 标注协议

| 字段 | 做法 |
|---|---|
| `answer_spans.quote` | **由定位工具从语料中截取**（保证逐字），不人工手打 |
| `char_range` / `chunk_index` | 工具按引文自动计算 |
| `expected_role` | **只看问题、不看文档** —— 避免主观 |
| `role_distractors` | 按"同事实 + 异角色"自动找候选，人工确认 |
| `answer_gist` | 人工一句话要点 |
| 多轮会话 | 优先从**真实会话**转写 |

### 8.1 文档角色表

| 角色 | 文件名关键词 |
|---|---|
| `court_finding` 法院认定 | 判决书 / 裁定书 / 调解书 / 决定书 |
| `party_claim` 当事人主张 | 上诉状 / 起诉状 / 答辩状 / 代理意见 / 律师函 |
| `evidence_fact` 证据事实 | 证据 / 口卡 / 户籍 / 人事档案 / 笔录 |
| `rule` 法规依据 | 法条 / 规程 / 指南 / 规定 / 司法解释 |
| `self_statement` 自制说明 | 情况说明 / 工作记录 / 思路 |

> 注意：**不存在"绝对权威"的文书**。若用户问的是"上诉状怎么主张的"，
> 正确来源就是上诉状（`expected_role = party_claim`）。
> 判定的是**问答是否对齐**，不是文档等级。
