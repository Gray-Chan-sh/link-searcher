## 一、可"按需安装"的扩展机制（架构想法）

### 项目里已有的三个"可选功能"先例（可直接复用其模式）

| 现有机制 | 位置 | 可复用的部分 |
|---|---|---|
| 按需下载模型 | `deps/catalog.rs` + `deps/download.rs` | 清单 + SHA-256 校验 + 进度事件，用时才下 |
| 可选 Web API | `webapi/`（70 路由，默认关） | 功能开关 + 独立进程 |
| 无 GUI 模式 CLI | `cli.rs`（`--data-dir` + `bootstrap_core`） | 同一份 core，另一个入口 |

### 形态对比

| 形态 | 能否"用时才装" | 侵入主程序 | 代价 |
|---|---|---|---|
| **A. sidecar 独立 exe + 清单** | ✅ | 无 | 数据契约 = 文件格式，有版本耦合 |
| B. 主程序编译期 feature flag | ❌ 要重出包 | 中 | 不是扩展，是"可选内置功能" |
| C. Tauri 插件 / WASM 插件 | 插件 ❌ / WASM ✅ | 高 | WASM 里跑不了 tantivy/rusqlite，宿主 API 得重造 |

> 关键事实：**Tauri 插件的"插件"是编译期依赖，不能后装**（`tauri-plugin-mcp` 即编译期依赖，且仅 debug 编译）。

### 倾向形态：A（sidecar）

```
<data_dir>/
  data.db  index/  ...          ← 主程序已有
  plugins/                       ← 新增
    lexicon-export/
      manifest.json              ← {id, version, entry, min_schema, scope, args}
      lexicon-export.exe
```

主程序只多一个「扩展」页：扫 `plugins/*/manifest.json` → 列出 / 启用 / 运行。

### 必须写进契约的硬约束

1. **SQLite 只读**：`mode=ro` 或 `PRAGMA query_only=1`；**严禁** `wal_checkpoint(TRUNCATE)` /
   `VACUUM` / 任何写操作。主程序跑 WAL（`db/mod.rs:26`），第二个 writer 会锁冲突甚至损坏库。
2. **Tantivy 只开 reader，绝不开 `IndexWriter`**：索引目录有锁，冲突直接报错。
3. **schema 版本守卫**：读 `app_settings.schema_version`（当前 `"8"`，`db/mod.rs:14`）与 manifest 的
   `min_schema` 比对，不匹配**直接拒绝**，不要猜着读。
4. **别按字段序号读 Tantivy**：`search/schema.rs:84` 的注释是历史教训——`md5` 必须最后加，因为插在
   中间会移位 field id、破坏所有旧 segment。扩展要按字段名取。
5. 一致性：扩展读到的是上一 commit 的索引快照，对批处理（导出类）完全够用。

> 通路：**本机扩展优先直接读数据文件**（Web API 默认关，要多养进程 + Token）；仅"跨机器/远程复用"才走 `webapi`。

## 三、词库导出（用全文 + 分词构建输入法词库）

### 定位

不是项目主要目的，而是**利用已有数据**产出的扩展功能。

### 可用数据

| 数据 | 位置 | 用途 |
|---|---|---|
| 全文（按 md5 去重） | `content_index.text_content` | 语料本体 |
| jieba 分词 + **词频/位置** | Tantivy `content` 字段（`WithFreqsAndPositions`，`search/schema.rs:57`） | 倒排索引已存 term→tf/df，可直接枚举词表 |
| POS 标注 / 词典判定 | `search/schema.rs` 的 `JIEBA`，`jieba.has_word()` / `tag()` | 过滤误标人名、判断通用词 |
| `hotword_counts` 表 | `db/mod.rs:349` | 现成的「词→计数」表（**当前为空**，`update_hotwords` 因写放大被删） |

缺件：**汉字→拼音**（crates.io `pinyin = "0.11"`；`pinyin_pro` 带多音字上下文消歧，更重）。

### 核心策略：只导出"输入法没有的词"

把语料所有高频词倒进输入法会**顶掉输入法自带常用词排序**，越用越难打。真正有增益的是语料里独有的
专有名词 / 机构名 / 行业术语。做法：**用目标输入法的原词库做差集**。

原词库可得性：

| 输入法 | 可得性 |
|---|---|
| Rime（小狼毫/鼠须管） | ✅ 明文 `.dict.yaml` |
| 搜狗 / QQ / 百度 | ⚠️ `.scel`/私有二进制，破解属灰色地带 |
| 微软拼音 | ❌ 私有 `.dat` |

现实做法：**不破解**，让用户用输入法官方「导出词库」功能导出明文，程序读该文件做差集。

**去重（是不是专有名词）与频次（是不是垃圾）正交，必须叠加**——OCR 噪声输入法同样没有。
差集按**词面**（字形串）比对，比对前统一 NFC / 大小写 / 全半角。

### 频次：排名 ≠ 只高频

- **tf**（语料内出现次数）：会被模板文档刷爆。
- **df**（出现在多少个不同文档）：✅ 比 tf 抗噪得多，是"高频"的好代理。
- **tf-idf**：要**避开**——IDF 高同时是"专有名词"和"孤例垃圾"的共性，会放大噪声。

稳定做法 = **双阈值 + 排名**：

- 硬门槛 `df ≥ 2`（至少两份文档出现）→ 砍掉绝大部分单例噪声
- 硬门槛 `tf ≥ 3`
- 再按 `tf × df`（或 `log(tf)×df`）排名取 top N 做**上限**

诚实说明：**语料频次 ≠ 打字习惯**。语料高频只说"该词曾在正经文本里被反复使用"，最擅长挑专有名词，
复刻不了手速。这也是它对**五笔**增益更直接的原因——五笔重码候选排序纯靠词频。

（进阶可选：新词发现常用的**凝固度 PMI + 左右邻字熵**，v1 属过度设计，先不上。）

### 两条技术路线：拼音 vs 五笔

| | 拼音 | 五笔 |
|---|---|---|
| 新增依赖 | `pinyin` crate（多音字有误差） | 码表数据文件（随包/自备） |
| 编码准确性 | 多音字会错 | 确定性，无歧义（需选 86/98/新世纪） |
| 语料词频的作用 | 增益有限（受内置权重压制） | 直接决定重码排序，增益明确 |
| 通用性 | 覆盖所有人 | 只有用五笔的人 |

五笔词码是**纯算法**（有字码即可算，不需词典）：

| 词长 | 编码规则 | 码长 |
|---|---|---|
| 2 字 | 各取前两码 | 4 |
| 3 字 | 前两字各取首码 + 第三字前两码 | 4 |
| 4 字 | 各取首码 | 4 |
| ≥5 字 | 前三字首码 + 末字首码 | 4 |

单字全码需现成码表（规则过绕），词码由字码推导。

### 建议

- 自用 + 用五笔 → **走五笔**（编码最省事、词频收益最大）
- 做成通用功能 → **先做拼音 + Rime `dict.yaml` 格式**，五笔作第二格式

### 整体流水线

```
语料 ──分词+统计(tf, df)──┐
                          ├─→ 候选词（df≥2 且 tf≥3）
原词库(用户导出)──normalize─┘        │
                                     ├─ 差集：只留输入法词库里没有的
                                     ├─ 过滤：2–4 字、纯 CJK、剔 PII(手机号/身份证/人名)
                                     ├─ 排名：tf×df 取 top N
                                     └─ 编码：拼音(需 pinyin 依赖) 或 五笔(需码表文件)
                                              ↓
                                      导出 Rime dict.yaml / txt
```

风险：多音字偏差（影响小）；人名/单位名属**个人隐私**，默认应过滤或需显式勾选。

## 四、同一文档多版本 → 如何确认"最终版"

### 前提：项目是"镜像"，不是版本库

Link-Searcher 反映的是**当前磁盘状态**，不保留版本历史。能否判"最终版"，先取决于历史版本**还在不在磁盘上**：

| 场景 | 库内结果 | 能否判终版 |
|---|---|---|
| **原地覆盖保存**（同一路径改版） | 同一条 `file_tracking` 行，md5/内容更新为最新；旧 md5 的 `content_index` 行变孤儿 → 被 `cleanup_orphan_content` 删掉 | ❌ 旧版本在库里彻底消失，无从比对 |
| **另存/改名**（"合同 v2.docx"） | 新文件新行，旧文件若仍在磁盘则保留 | ✅ 多版本共存，可比对 |
| **旧版本被删/移走** | 该行被回收 | ❌ 同上 |

### 必须知道的机制：移动检测会折叠同族

`scanner/mod.rs:695-758`：遍历时若"某条已跟踪记录 A 的路径从磁盘消失，而同目录出现**同名同大小**
的文件 B" → 判为移动 → 只留一条（`size ≤ 10MB` 时还会比对 md5 确认）。

- 后果：它**刻意不留"同族两份"**（注释写明了是"防幽灵残留"）。
- 所以文件在目录间搬动**不会**伪装成"两个版本"。
- 反向：**真正的改版**（内容变了 → 大小大概率也变）不会命中该分支，会各自成行 ✅。
- 另：md5 相同的内容共享 `content_index` 同一行（按 md5 去重）；逐字节相同的副本本来也无所谓谁是终版。

### 核心认知

**"最终版"不是文件属性，是语义判断**——磁盘上没有任何字段记录它。只能做**证据聚合 + 打分 + 用户裁定**，
不能全自动断言。

### 第一步：分族（哪些文件是同一份文档的不同版本）

| 强度 | 信号 |
|---|---|
| 强 | 同目录 + **文件名主干归一化后相同**（剥离 `v1/v2/终版/定稿/最终/final/(1)/副本/备份/2024-01-01`） |
| 中 | 内容 **simhash/MinHash** 海明距离 ≤ 阈值 |
| 弱 | `doc_embeddings` 余弦 ≥ 阈值 |
| — | md5 相同 → 已由去重/移动检测折叠 |

### 第二步：族内打分（证据加权）

| 证据 | 方向 | 权重 |
|---|---|---|
| 文件名标记：终版/最终/final/定稿/批准 | + | 高 |
| **正文"修订记录/版本记录"表里的日期/版本号最大** | + | 高 |
| 文件名里的日期/版本号最大 | + | 中高 |
| 含签章/批准/生效日期（PDF 印章检测已有基础） | + | 高 |
| 路径含"归档/最终/定稿"；**不含** old/备份/历史/回收 | + | 中 |
| `char_count` / `file_size` 最大（内容最全） | + | 低中 |
| `mtime` 最新 | + | **中（不可靠，降权）** |
| 路径/名含 备份/copy/副本/旧/(1) | − | 中 |
| `quality_flags` 命中（扫描件/乱码版本） | − | 中 |

### 第三步：只给建议，最终用户裁定

- **绝不自动删除/覆盖任何文件**
- 新表 `doc_version_groups(group_key, file_id, role, score, reasons, decided_by)`，
  `decided_by=user` 优先于 `=auto`
- UI：浏览页里同族折叠 → 展开时间线 → 高亮"建议终版 + 理由" → 一键"设为终版"

### 第四步（最准、最贵）：LLM 读正文的修订记录表

中文公文/合同/方案**正文里通常自带"修订记录/版本记录"表**（版本号、日期、拟稿/审核/批准）。
这是**最可靠的信号——文档自己写了谁是终版**。项目已有 LLM 网关 + `anydoc`/`calamine`（Office 表格）
+ `lopdf`（PDF），可把该表抽出喂给 LLM 判族内终版，命中率最高。

### 时间信号为什么不能单独用

- `mtime`：复制（robocopy/cp）会保留、浏览器下载会重置 → 经常"假新/假旧"
- `file_tracking.created_at`：是**程序首次看到它的时间**，不是文件创建时间；且只在应用持续运行时才可靠
- 结论：时间是**辅助加权**，不能当判据

另一个语义坑：**"最新修改的" ≠ "最终生效的"**（退回修改稿常常比定稿更新）。输出至少分三档：
**最新修改 / 内容最全 / 已定稿（有批准或签章）**。

### 不写代码也能用的土办法

全文都已索引 → **直接用搜索定位同族**：搜一份文档里独有的句子或标题，浏览页列出全部命中文件 →
人工在预览面板比对（预览面板已有高亮）。

### 需要新增的能力

| 能力 | 新增内容 | 难度 |
|---|---|---|
| 文件名版本标记词典 + 主干归一化 | 正则（中英） | 低 |
| simhash / MinHash | 基于已有 `sha2` 做 shingle hash，或加 crate | 低 |
| 修订记录表抽取 | 复用 `anydoc`/`calamine`/`lopdf` | 中 |
| 族内 LLM 比对 | 复用 AI 网关 | 中 |
| 版本分组表 + 浏览页族视图 | 新表 + UI | 中 |
| 签章/批准检测 | 复用 PDF 水印/图像检测 | 中高 |

> 该功能同样适合做成扩展（只读 `data.db` + `index/`），与词库导出共用一套机制。
